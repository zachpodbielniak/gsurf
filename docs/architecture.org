#+TITLE: gsurf Architecture
#+OPTIONS: toc:2 num:nil

* Overview

All browser logic lives in =libgsurf.so=. The =gsurf= binary (=src/main.c=) only
parses options, loads config, builds the application, and runs the GLib main
loop. This keeps gsurf embeddable: a host application can drive its own main loop
and link =libgsurf= directly.

* Object model

| Type                  | Kind                | Role                                              |
|-----------------------+---------------------+---------------------------------------------------|
| =GsurfApplication=    | final GObject       | Session: owns config, module manager, windows.    |
| =GsurfWindow=         | abstract derivable  | Container of N views; backend subclasses.         |
| =GsurfView=           | abstract derivable  | One web view; backend subclasses.                 |
| =GsurfConfig=         | final (public struct)| YAML configuration + retained =modules:= mapping. |
| =GsurfSettings=       | final (public struct)| Backend-agnostic web engine settings.             |
| =GsurfConfigCompiler= | final GObject       | Compiles =config.c= via crispy, calls init.       |
| =GsurfModule=         | abstract derivable  | Base class for loadable modules.                  |
| =GsurfModuleManager=  | final GObject       | Loads modules, dispatches hooks.                  |
| =GsurfContainerRegistry= | final GObject (singleton) | Containers: placement policy, native sessions. |
| =GsurfContainer=      | final GObject       | One container: id, name, colour, temporary, views. |
| =GsurfHostRules=      | final GObject       | Ordered per-host regex rules with YAML settings.  |

The abstract =GsurfView= exposes =load_uri=, =reload=, =go_back/forward=,
=get_uri/title=, =run_javascript_async=, =apply_settings=, =get_native_widget=
(as =gpointer=), etc., plus signals =load-changed=, =uri-changed=,
=title-changed=, =progress-changed=, =web-process-terminated=.

** View identity, opener and container

Every =GsurfView= gets a process-unique =id= at construction (=gsurf_view_lookup()= finds a live view by it). Construct-only properties record where it came from:

- =opener= — the view it was opened from (link in a new view, link hint, popup), held weakly; =gsurf_view_get_opener_id()= keeps the id after the opener closes. The tabs module builds its tree from this (see [[file:tabs.org][tabs.org]]).
- =container-id= — the requested container; after construction it reads back the container the registry chose (=NULL= = default).
- =related= — an engine popup that shares its opener's web process and session. WebKit requires a popup to live in its opener's session, so a related view is always placed in the opener's container.
- =initial-uri= — the URI the creator is about to load, a placement hint only.

Create views with =gsurf_view_new_full(opener, container_id, initial_uri, related)=; =gsurf_view_new()= passes nothing. =main.c= passes the opener for every view it opens (link in new view, middle/Ctrl-click, popups) and the startup URI as the first view's hint; the =modal= (=F= hints) and =mcp= (=open_view=) modules do the same.

** Containers

A container is a separate browsing identity (cookies, storage, cache). =GsurfContainerRegistry= (=src/core/=) is backend-agnostic:

1. In its =constructed()=, the =GsurfView= base class asks the registry to *resolve* the view's container: a related popup takes its opener's; otherwise a resolver installed by policy (the =containers= module) decides, else the requested id. =temporary= creates a fresh =tmp-N= container; =default= (=GSURF_CONTAINER_DEFAULT=) explicitly asks for the default container, which a =NULL= request does not (it leaves the choice to the resolver); an unknown id falls back to the default container with a warning. =temporary=, =default= and the =tmp-= prefix are reserved and cannot name a persistent container.
2. It then *acquires* the container's native session (created on first use) before the backend subclass builds its native web view, and *releases* it on dispose.
3. The backend supplies the sessions through a =GsurfSessionBackend= vtable (=src/backend/webkit/gsurf-webkit-session.c=), installed from the view class's =class_init= so it exists before the first view: a =WebKitWebContext= with its own website data manager on WebKitGTK 4.1, a =WebKitNetworkSession= on 6.0. Persistent containers store data in =$XDG_DATA_HOME/gsurf/containers/<id>= and cache in =$XDG_CACHE_HOME/gsurf/containers/<id>= (both 0700, cookies in =cookies.sqlite=); temporary containers are ephemeral and are destroyed =temp_cleanup_delay= seconds after their last view closes (or if no view ever uses them).
4. Every session — the default one included — gets the same setup from the config (TLS policy, cache model, cookie storage, proxy), web-process extensions, and a once-per-session download hook. =gsurf_container_registry_set_policy()= applies ITP and a cookie accept policy to all of them, now and as they are created; =session-created= lets modules configure new ones further.

The default container is the engine's default session with the =cookie_jar:= file, exactly as before; without the =containers= module nothing changes. Policy on top of the registry (host rules, temporary tabs, reopening a tab in another container) is the =containers= module: see [[file:containers.org][containers.org]].

** Main-frame responses

WebKit's navigation policy decision (=before_navigate=) is also made for iframe navigations and cannot tell them from top-level ones: WebKitGTK exposes no main-frame flag there. The response policy decision does (=webkit_response_policy_decision_is_main_frame_main_resource()=), so the WebKit backends (GTK3, GTK4 and LRG) report every displayable main-frame response to =GsurfNavigationHook::decide_main_response= through =gsurf_module_manager_dispatch_main_response()=; =GSURF_POLICY_IGNORE= cancels the load and the view keeps its page. Downloads and sub-resources are not reported. The request has already been sent by then, so a hook that must act before any request (privacy) also checks =before_navigate= for the loads it can recognise as top-level.

** Script worlds and messages

Modules can run code in an isolated script world — sharing the page's DOM but not its JavaScript globals — and receive messages from it: =gsurf_view_add_user_script_in_world()=, =gsurf_view_run_javascript_in_world_async()= / =_finish()= (the result's source object is the =GsurfView=), and =gsurf_view_register_script_message(view, name, world)=, whose messages arrive as the detailed signal =script-message::<name>= with the posted value as JSON. Backends without worlds ignore registration and complete evaluations with =G_IO_ERROR_NOT_SUPPORTED=.

* Backend abstraction

The web engine is reached only through =GsurfView= / =GsurfWindow=. Exactly one
backend compiles per build (=GTK_BACKEND=):

- =gtk3= → =GsurfWebkit2View= + =GsurfGtk3Window= (WebKit2GTK 4.1 / GTK3).
- =gtk4= → =GsurfWebkit6View= + =GsurfGtk4Window= (WebKitGTK 6.0 / GTK4).

=src/core/gsurf-backend.c= is the only file that knows both backends, behind
=#ifdef GSURF_BACKEND_*=. It provides the =gsurf_view_new()= /
=gsurf_window_new()= factories and =gsurf_backend_init()=. GTK/WebKit headers
appear only under =src/backend/<backend>/=.

Modules are compiled per backend too (the module Makefiles receive =GTK_BACKEND=, and =GSURF_BACKEND_GTK3= or =GSURF_BACKEND_GTK4= is defined). The window-chrome modules =chromebar=, =find_bar=, =status_bar= and =tabs= build on both: their GTK calls go through the header-only, module-private =modules/include/gsurf-chrome-compat.h= (static inline wrappers for entry text, box packing, show/hide, detaching a widget from the chrome, CSS classes and providers, native favicons, clicks, and key-press handling: =key-press-event= on GTK3, a capture-phase =GtkEventControllerKey= on GTK4). It lives outside =src/= on purpose, so it is neither installed nor GIR-scanned. A module that fails to compile fails =make modules=.

** Window order and side chrome

=GsurfWindow= keeps an ordered view list. =gsurf_window_insert_view()= places a view at an index (the tab tree puts a child right after its parent's subtree), =gsurf_window_move_view()= reorders and emits =view-moved (view, from, to)=, =gsurf_window_reopen_view(window, view, container_id)= reopens a view's page in another container in its place (a new view with the same opener, made active, then the old one removed; the window emits =view-added=, then =view-replaced (old, new)=, then =active-view-changed= for the new view, then =view-removed= for the old one, so chrome — a tab tree, a window layout — hands over the old view's place before activation would move the new view elsewhere), and =gsurf_window_get_view_index()= finds a view. The native stack has no visible order, so only the list changes. Besides top and bottom chrome, =gsurf_window_add_side_widget(window, widget, GSURF_CHROME_EDGE_LEFT|RIGHT)= packs a side panel between them (GTK3 and GTK4: a horizontal box around the view stack; no-op on LRG and in kiosk mode). The panel never expands: it keeps its size request and the view stack takes the remaining width (on GTK4 the window sets the panel's hexpand to FALSE explicitly, which stops GTK4 from propagating an expanding descendant up to it).

** Window layouts (panes)

By default a window shows one view at a time: the GTK backends keep every view widget in a private =GtkStack= and show the active one. A *window layout* replaces that stack with its own widget so several views can be on screen at once (the =wmux= module's panes; an embedder could implement its own). It is the =GsurfWindowLayout= interface (=src/window/gsurf-window-layout.h=):

| vfunc | When the window calls it | What the layout does |
|-------+--------------------------+----------------------|
| =get_root= | while installing | returns its native root widget (it keeps its own reference) |
| =attach= / =detach= | first / last call for a window | builds / drops per-window state; =detach= unparents every view widget it holds |
| =add_view= | a view joined the window, or was in it at install time | parents the view's widget in a pane, or keeps it as an unparented background view; must not focus it |
| =remove_view= | a view leaves the window | unparents its widget (the window then activates the neighbour as usual) |
| =activate_view= | a view became the active view | shows it (puts it in a pane) and focuses it |
| =is_view_visible= (optional) | =gsurf_window_get_view_visible()= | whether the view is on screen; default: only the active view |
| =serialize= / =restore= (optional) | the session module | a string describing the arrangement, views by saved index, and back |

=gsurf_window_set_layout(window, layout)= installs one: every view widget leaves the stack (the backend's =remove_view=), then =attach=, =add_view= for each view in window order, =activate_view= for the active view, and finally the new backend class vfunc =set_content(window, root)= packs the root where the stack was (GTK3 and GTK4: right after the hidden stack in the horizontal box between the side panels; GTK3 hides the stack with no-show-all so =gtk_widget_show_all()= cannot bring it back, and only =gtk_widget_show()= the root so a layout's hidden parts stay hidden). =gsurf_window_set_layout(window, NULL)= reverses it: =detach=, =set_content(NULL)= brings the stack back, every view widget is re-inserted into the stack in window order and the active one is shown and focused. Installing over a layout removes the old one first. Each change emits =visible-views-changed= once; setting the same layout again (or =NULL= when none is set) does nothing. The window holds a reference to the layout and removes it when disposed (the GTK backends do it before destroying their toplevel).

While a layout is set the abstract window routes view changes to it instead of the stack: =gsurf_window_insert_view()= calls the backend's new =connect_view= vfunc (per-view event wiring only: mouse buttons, and on GTK4 focus) and then the layout's =add_view=; =gsurf_window_remove_view()= calls the layout's =remove_view=; =gsurf_window_set_active_view()= calls its =activate_view=. The backends' =insert_view= is safe to call again for a view already stacked (it re-inserts on removal of a layout) and wires each widget once per window, and =remove_view= only removes a widget whose parent is the stack. A layout that leaves a widget parented when it should not gets a warning instead of a GTK critical.

=gsurf_window_set_layout()= returns =FALSE= with a warning (logged once per window) in kiosk mode, which shows one view by design, and on backends without =set_content= — the libregnum backend renders the page to a texture and has no widget tree to put a layout's root in.

*Visibility.* =gsurf_window_get_view_visible(window, view)= says whether a view is on screen: without a layout only the active view is (a change is announced by =active-view-changed=); with one the layout decides, and announces changes by calling =gsurf_window_layout_notify_visible(window)=, which emits =visible-views-changed=. Chrome (the tab tree) marks visible tabs from it.

*Focus follows click.* While a layout is set, a view that takes keyboard focus — a click into it (WebKit grabs focus on a press), Tab — becomes the active view, if it is visible (a background view never becomes active this way). GTK3 follows the toplevel's =GtkWindow::set-focus= (after the change), which also fires while the window is in the background; GTK4 adds a =GtkEventControllerFocus= (=enter=, named =gsurf-view-focus=) to each view widget. =gsurf_window_set_active_view()= returns early for the active view, so the layout's own focusing in =activate_view= does not loop.

*Key grab.* =gsurf_window_set_key_grab(window, TRUE)= makes every key press reach =GsurfWindow::key-press= even while the user types: GTK3 no longer runs =gtk_window_propagate_key_event()= into a focused chrome entry first, GTK4 skips its early return for bare keys in an editable, and the =gsurf= binary skips its typing guard (a focused page field or modal INSERT passthrough would otherwise send a bare key straight to the page). A key the handlers decline still reaches the focused widget. A module sets the grab after its prefix key (wmux =C-b=) so the next key is a command wherever focus is, and clears it once that key is handled; Escape reaches modules as usual.

** Code shared by the WebKit backends

=src/backend/webkit/= holds what GTK3/4.1 and GTK4/6.0 share: content filters and web-process extensions (=gsurf-webkit-content.c=), gopher/gemini (=gsurf-webkit-protocol.c=), per-container sessions (=gsurf-webkit-session.c=), and the module-facing signal handling (=gsurf-webkit-common.c=: context-menu entries, download destinations, TLS exceptions — scoped to the view's own session — permission requests, hovered links, popup creation). Both backends therefore offer the same features: popups, favicons, downloads, TLS exceptions, context-menu entries, snapshots and clipboard on GTK4 as on GTK3.

* Event flow

#+begin_example
main.c
  └ parse options; load GsurfConfig (embedded default, then YAML file)
  └ compile + load config.c (crispy) -> gsurf_config_init()
  └ GsurfApplication
  └ GsurfModuleManager: load MODULEDIR, read each module's enabled+config,
                        activate enabled modules
  └ GsurfWindow + GsurfView; apply settings; connect signals
  └ load URI (URI-handler modules may rewrite it)
  └ g_main_loop_run()           (GLib main context; no GTK-main assumption)

key press → window "key-press"
  └ module manager dispatch_key_event (modal/hints/tabs modules)  [first TRUE wins]
  └ else core keybind table (GsurfConfig) -> GsurfAction -> execute
      show-keybinds (`?`) collects core + active GsurfKeybindProvider
      modules and pops a help overlay (GTK dialog or in-page fallback);
      overlay keys: hjkl move, q/?/Escape close

mouse press on a view widget → window "button-press"
  (GTK3: the widget's button-press-event; GTK4: a capture-phase
   GtkGestureClick for any button, named "gsurf-view-click", that claims
   the press when a handler consumes it)
  └ module manager dispatch_mouse_event  [first TRUE wins]
  └ else core mousebind table (GsurfConfig) -> GsurfAction -> execute

navigation/load → view signals
  └ dispatch_load_changed / dispatch_after_navigate to navigation-hook modules

title-changed of the ACTIVE view → window title "Title — gsurf"
  (other views' titles are ignored, so a background tab or another pane
   finishing a load never renames the window; active-view-changed shows
   the new active view's title; an untitled view that never loaded keeps
   the configured window title)
#+end_example

* Configuration pipeline

1. =GsurfConfig= is created with built-in defaults.
2. The embedded =default-config.yaml= is parsed.
3. The user's =~/.config/gsurf/config.yaml= is merged over it.
4. An optional =~/.config/gsurf/config.c= is compiled (crispy) and its
   =gsurf_config_init()= runs against =gsurf_config_get_default()=, overriding
   anything.
5. Modules read their own section via =gsurf_config_get_module_node()=.
